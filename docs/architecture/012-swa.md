# ADR 012: Secure Web Authentication (SWA)

- Status: Accepted (2026-11-08). Migration 0040. Builds on ADR 010 (applications).
- Last resort. SAML (ADR 011) or OpenID Connect are always preferable: with SWA the identity provider holds a **password for another system**, which is the most sensitive thing it can store. Use it only for legacy applications that have nothing but a username/password form.

## What exists
- Sign-on method **Secure Web Authentication**; its facet is `swa_configs` (1:1 with the application): login URL (the form's `action`), username and password field names, up to 10 fixed hidden fields, and where the username comes from (the user types it | their email | their username).
- `swa_credentials`: one row per (application, user): optional username, the password as **AES-256-GCM** ciphertext, key id, timestamps, last use.
- Flow: My apps tile → UI `/swa/continue?app=ID` → first time: the user enters their account at that application (shown with the destination host) → `POST /api/v1/swa/apps/{id}/launch` returns the form fields → the page builds a hidden `<form method=POST>` and submits it to the registered login URL. Later launches need no typing. The tile has a "change saved sign-in" action (`?manage=1`).
- Admin UI: SWA card (login URL, fields, username source), list of who has stored a sign-in (no secrets), per-user reset. `SWA_ENCRYPTION_KEY` unset shows a warning and users cannot save passwords.

## Security decisions
- **No browser extension, no scraping.** The credential is sent only by an HTTP POST from the user's browser to the exact URL an administrator registered: https (http only for localhost in development), no userinfo, no fragment. Never a GET or a URL parameter, so it cannot land in logs, history or `Referer`.
- **Encryption**: `cryptography`'s AES-GCM; the key is HKDF-derived from `SWA_ENCRYPTION_KEY` (32 random bytes, its own key, not shared with MFA/OIDC keys). The **AAD binds tenant, application and user**, so a ciphertext copied to another row does not decrypt (tested). Fresh random nonce per write. A `key_id` supports rotation: put the old key in `SWA_ENCRYPTION_KEY_PREVIOUS`; rows are re-encrypted with the new key the next time they are used. No key configured = nothing is written or read (fail closed).
- **No endpoint returns a stored password except the launch**, and the launch only answers the owner. Administrators can list who stored one, see the username only if the user typed it, and reset it; they can never read it. No password in audit events, logs or error messages; responses are `Cache-Control: no-store`.
- **Release is gated**: signed-in, **entitled** (SWA always requires an assignment, whatever `require_assignment` says), active application, valid CSRF token and Origin, **signed in within `SWA_FRESH_AUTH_SECONDS` (15 min)** else `403 reauthentication_required` and the UI makes the user sign in again. A stolen but older session cookie therefore cannot pull passwords out. Per-user rate limits on launch and on saving.
- **Admins cannot redirect stored passwords**: changing the login URL deletes every stored credential for that application (audited with the new URL). The entry form always shows the destination host.
- **The IdentityForge password cannot be stored** (checked with the user's own Argon2 hash), so this vault does not become a copy of the account's password.
- Stored credentials of users who lose access are deleted by the existing purge job; deleting the user, the application, or the SWA configuration deletes them immediately.
- Unassigned, unknown and inactive applications all answer 404.

## Known limits / residual risk
- The password reaches the user's browser (JavaScript and the DOM) for an instant. A cross-site-scripting bug in IdentityForge's UI could read it; the freshness rule limits how long a stolen session can do this but does not remove it. The UI sets no Content-Security-Policy beyond frame-ancestors yet. A server-side or extension-based design would avoid it but cannot work for ordinary web forms.
- Works only for forms that accept a plain cross-site POST. Pages needing a CSRF token fetched first, JavaScript-built login, CAPTCHA or MFA at the target do not work.
- A malicious or compromised **administrator** can point an application at a host they control; existing passwords are wiped when they do, but users who then re-enter a password would send it there. The destination is shown to users and the change is audited. Registering applications is a super-admin-grade trust.
- The target application is not told about password changes made in IdentityForge and vice versa; users update their stored password themselves.
- The encryption key sits in the same environment as the database credentials; use a secrets manager in production. Losing the key makes stored passwords unreadable (users enter them again).
- No shared/administrator-set accounts and no password rotation by IdentityForge: deliberately out of scope.
